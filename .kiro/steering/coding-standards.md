# 编码规范与代码质量标准

## 通用原则

- **Clean Architecture**：分层清晰，依赖方向一致（外层依赖内层）
- **SOLID**：单一职责、开闭、里氏替换、接口隔离、依赖倒置
- **模块化**：高内聚、低耦合，避免循环依赖

## 代码风格

- 命名：见名知意，统一风格（如 camelCase / snake_case 按项目约定）
- 函数：短小、单一职责，参数不宜过多
- 注释：解释「为什么」而非「做什么」，公共 API 必须文档化

## 质量要求

- 算法效率：使用最高效的算法与数据结构
- 模块化：编写模块化代码，将复杂逻辑拆分为更小的原子部分；尽可能拆分为类、文件、目录、模块、函数等
- 文件管理：将过长的文件拆成更小、更易维护的文件，并保持函数粒度更小
- 导入语句：优先从其它文件导入函数，而不是直接修改那些文件
- 文件组织：将文件组织到清晰的目录结构中
- 复用：优先复用已有代码，而不是从零编写
- 代码保留：保留有效实现；非必要不要改动已正常工作的组件
- 系统化顺序：在开始下一步前先把当前步骤完整做完；保持功能实现的系统化顺序
- 设计模式：为可维护性选择合适的设计模式；面向未来变化进行规划，保证可扩展、灵活、可伸缩、可维护
- 关键路径有单元测试或集成测试
- 错误处理明确，避免静默失败
- 不提交调试代码、敏感信息、大文件
- 确保代码的稳定性或可扩展性
- 关注代码性能或安全性方面的问题
- 代码生成时添加必要的注释

## 测试与脚本规范

### 测试文件位置

- **所有测试文件**：统一放在 `tests/` 目录
- **单元测试**：`tests/test_*.py`（如 `test_chat_api.py`）
- **集成测试**：`tests/test_*.py`（如 `test_retrieval_service.py`）
- **性能测试**：`tests/test_perf_*.py`（如 `test_perf_monitoring.py`）
- **功能验证脚本**：`tests/test_*.py`（如 `test_streaming.py`）

### 测试脚本规范

- 测试脚本必须包含清晰的文档字符串说明用途
- 使用 `#!/usr/bin/env python3` 作为脚本开头
- 包含使用说明和示例
- 支持命令行参数（使用 `argparse` 或环境变量）
- 输出清晰的测试结果（使用 emoji 标记：✅ ❌ ⚠️ 💡）
- 包含错误处理和友好的错误提示

### 示例测试脚本结构

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""
功能测试脚本

用法：
    python tests/test_feature.py

说明：
    测试某个功能的具体行为
"""
import os
import sys

def test_feature():
    """测试主函数"""
    print("🚀 开始测试...")
    # 测试逻辑
    print("✅ 测试通过")

if __name__ == "__main__":
    test_feature()
```

### scripts/ 目录用途

- `scripts/` 目录仅用于**运维脚本**和**数据迁移脚本**
- 例如：`scripts/run_migrations.py`、`scripts/migrations/`
- 不要在 `scripts/` 中放置测试脚本

## 改进与进一步推进

每次代码实现后，考虑以下方面：

- S1：提出提升代码稳定性或可扩展性的方式
- S2：提供增强性能或安全性的策略
- S3：推荐提升可读性或可维护性的方法
- 推荐值得进一步调查/验证的方向
