# AkShare 数据集成需求文档

## 功能概述

将 AkShare 真实基金数据集成到现有的多模态输出系统中，替换模拟数据，实现从数据获取、转换到前端展示的完整链路。

## 业务背景

当前系统的基金分析功能使用模拟数据，无法提供真实的基金信息。通过集成 AkShare 数据源，可以：
- 提供真实、准确的基金数据
- 支持 8 种核心数据类型（基本信息、业绩表现、资产配置、净值走势等）
- 增强用户体验和系统可信度

## 用户故事

### US-1: 作为用户，我希望查看单只基金的真实数据分析
**描述**：用户输入基金代码或名称，系统返回包含真实数据的多模态分析结果

**验收标准**：
- [ ] 能够获取并展示基金基本信息（名称、代码、类型、规模、经理等）
- [ ] 能够展示真实的业绩表现数据（近1月、3月、6月、1年、3年收益率）
- [ ] 能够展示真实的资产配置环形图（股票、债券、现金、其他占比）
- [ ] 能够展示真实的净值走势折线图（近1年数据）
- [ ] 能够展示费率信息（管理费、托管费、申购费、赎回费）
- [ ] 能够展示风险指标（波动率、夏普比率、最大回撤）
- [ ] 数据缺失时能够优雅降级（隐藏对应模块或显示提示）
- [ ] 数据获取失败时能够返回纯文本分析（兜底机制）

### US-2: 作为用户，我希望对比多只基金的真实数据
**描述**：用户输入多个基金代码，系统返回包含对比表格和图表的分析结果

**验收标准**：
- [ ] 能够同时获取多只基金的数据（支持 2-5 只基金对比）
- [ ] 能够展示业绩对比表格（各时间段收益率对比）
- [ ] 能够展示费率对比表格
- [ ] 能够展示净值走势对比折线图
- [ ] 能够展示投资风格对比雷达图（如果数据可用）
- [ ] 对比结果清晰，高亮显示关键差异
- [ ] 数据获取失败时能够部分展示（已获取的基金数据）

### US-3: 作为系统管理员，我希望系统能够稳定获取 AkShare 数据
**描述**：系统能够可靠地从 AkShare 获取数据，并处理各种异常情况

**验收标准**：
- [ ] 请求失败时有重试机制（最多 3 次，指数退避）
- [ ] 有请求限流机制（避免被封 IP）
- [ ] 有缓存机制（减少重复请求，TTL: 1小时）
- [ ] 有完整的错误日志（包含 traceId、answerId、错误详情）
- [ ] 有性能监控（记录各阶段耗时）
- [ ] 数据格式异常时能够识别并处理

### US-4: 作为开发者，我希望系统架构清晰，易于维护和扩展
**描述**：代码结构清晰，模块职责明确，易于添加新的数据类型

**验收标准**：
- [ ] 数据获取层独立封装（AkShareClient）
- [ ] 数据转换层独立封装（fund_formatter）
- [ ] Agent 层只负责编排和调用
- [ ] 有完整的单元测试（覆盖率 > 80%）
- [ ] 有集成测试（端到端测试）
- [ ] 有清晰的文档和注释

## 功能需求

### FR-1: AkShare 数据获取
**优先级**：P0（必须）

**描述**：封装 AkShare 数据获取逻辑，提供统一的数据访问接口

**详细需求**：
1. 创建 `AkShareClient` 类，封装 8 种数据获取方法：
   - `get_basic_info(symbol)` - 基本信息
   - `get_achievement(symbol)` - 业绩表现
   - `get_analysis(symbol)` - 风险指标
   - `get_detail_hold(symbol)` - 资产配置
   - `get_detail_info(symbol)` - 费率信息
   - `get_nav_data(symbol, period)` - 净值走势
   - `get_industry_allocation(symbol, date)` - 行业配置
   - `get_portfolio_hold(symbol, date)` - 持仓明细

2. 异常处理：
   - 网络请求失败：重试 3 次，指数退避（1s, 2s, 4s）
   - 数据格式异常：记录日志，返回空数据结构
   - 基金代码不存在：返回明确的错误信息

3. 性能优化：
   - 请求限流：每次请求间隔 0.5-1 秒
   - 缓存机制：使用内存缓存，TTL 1 小时
   - 并发控制：最多 3 个并发请求

### FR-2: 数据转换与格式化
**优先级**：P0（必须）

**描述**：将 AkShare 原始数据转换为前端可渲染的结构化 JSON

**详细需求**：
1. 增强现有的 `fund_formatter.py`：
   - 支持 AkShare 数据格式
   - 处理字段名差异（映射层）
   - 处理数据缺失（默认值、隐藏模块）

2. 支持的输出类型：
   - 卡片：基本信息、费率信息、核心表现
   - 表格：业绩对比、费率对比、持仓明细
   - 图表：环形图（资产配置）、折线图（净值走势）、雷达图（风格对比）、柱状图（行业配置）

3. 数据质量保证：
   - 数值格式化（百分比、金额）
   - 日期格式统一
   - 空值处理

### FR-3: Agent 层集成
**优先级**：P0（必须）

**描述**：修改 ProductInterpretAgent 和 ProductCompareAgent，使用 AkShare 数据

**详细需求**：
1. ProductInterpretAgent（单基金解读）：
   - 调用 AkShareClient 获取数据
   - 调用 fund_formatter.build_single_output() 生成结构化输出
   - 调用 LLM 生成分析文本
   - 合并数据和文本，返回完整的 FundAnalysisOutput

2. ProductCompareAgent（多基金对比）：
   - 并发调用 AkShareClient 获取多只基金数据
   - 调用 fund_formatter.build_compare_output() 生成对比输出
   - 调用 LLM 生成对比分析文本
   - 合并数据和文本，返回完整的 FundAnalysisOutput

3. 兜底机制：
   - 数据获取失败：返回纯文本分析（不含图表）
   - 部分数据缺失：隐藏对应模块，展示可用数据
   - 全部失败：返回友好的错误提示

### FR-4: 前端兼容性验证
**优先级**：P1（重要）

**描述**：确保前端能够正确渲染 AkShare 真实数据

**详细需求**：
1. 使用真实数据测试所有前端组件
2. 验证图表配置正确性
3. 验证表格数据展示
4. 验证卡片数据展示
5. 修复发现的兼容性问题

### FR-5: 扩展数据类型（可选）
**优先级**：P2（可选）

**描述**：支持行业配置和持仓明细展示

**详细需求**：
1. 行业配置柱状图：
   - 展示前 10 大行业配置
   - 显示占净值比例

2. 持仓明细表格：
   - 展示前 10 大重仓股
   - 显示股票代码、名称、占比

- 系统可用性 > 99%

### NFR-2: 可靠性要求
- 数据获取成功率 > 95%
- 异常场景有完善的兜底机制
- 错误日志完整，便于排查问题

### NFR-3: 可维护性要求
- 代码结构清晰，模块职责明确
- 单元测试覆盖率 > 80%
- 有完整的文档和注释

## 数据需求

### 数据源
- **主要数据源**：AkShare（雪球 + 东方财富）
- **数据更新频率**：
  - 净值数据：每日更新（交易日）
  - 持仓数据：季度更新
  - 资产配置：季度更新
  - 业绩数据：实时更新

### 数据类型
1. **基本信息**：基金代码、名称、类型、规模、经理、成立日期等
2. **业绩表现**：各时间段收益率、同类排名、最大回撤
3. **风险指标**：波动率、夏普比率、最大回撤
4. **资产配置**：股票、债券、现金、其他占比
5. **费率信息**：管理费、托管费、申购费、赎回费
6. **净值走势**：逐日单位净值和日增长率
7. **行业配置**：各行业占净值比例（可选）
8. **持仓明细**：前十大重仓股及占比（可选）

### 数据质量要求
- 数据准确性：与 AkShare 官方数据一致
- 数据完整性：关键字段不能缺失（基金代码、名称、类型）
- 数据时效性：缓存数据不超过 1 小时

## 约束条件

### 技术约束
- 必须使用 AkShare 1.18.54 或更高版本
- 必须兼容现有的 fund_formatter.py 接口
- 必须遵循项目的 Python 后端开发规范
- 必须使用 asyncio 进行异步数据获取

### 业务约束
- 不能影响现有功能的正常使用
- 必须保留纯文本兜底机制
- 数据获取失败不能导致系统崩溃

### 时间约束
- 核心功能（FR-1, FR-2, FR-3）必须在 2 周内完成
- 扩展功能（FR-5）可以在后续迭代中完成

## 风险与应对

### 风险 1：AkShare 数据源不稳定
**影响**：高  
**概率**：中  
**应对策略**：
- 添加重试机制（3 次重试，指数退避）
- 添加缓存机制（减少实时请求）
- 添加兜底机制（返回纯文本分析）

### 风险 2：数据格式变化
**影响**：中  
**概率**：低  
**应对策略**：
- 添加数据格式校验
- 添加版本检测
- 添加告警机制

### 风险 3：性能问题
**影响**：中  
**概率**：中  
**应对策略**：
- 使用缓存减少请求
- 使用并发提升速度
- 对净值数据进行降采样

### 风险 4：前端兼容性问题
**影响**：低  
**概率**：低  
**应对策略**：
- 使用真实数据进行充分测试
- 添加前端数据校验
- 添加默认值处理
